# 관계와 원문을 검색하는 GraphRAG 실습

지난 단원의 Neo4j 연결과 `run_cypher`를 이어 사용합니다. 교안 01은 관계 조회·벡터 검색 에이전트를 각각 실행하고, 교안 02는 같은 도구를 한 에이전트에 연결합니다.

벡터 검색은 `VectorRetriever`로 원문 청크·출처·유사도를 반환합니다. 관계가 필요하면 별도 `search_graph` 도구를 사용합니다. 문서 벡터는 배포 파일을 재사용하고 검색 질문만 임베딩합니다.

## 데이터

| 자료 | 개체 노드 | 도메인 관계 | 벡터 검색 원문 | 청크 |
|---|---:|---:|---|---:|
| Movies 원본 샘플 전체 | 171(영화 38·인물 133) | 253 | 위키백과 도입부·전체 줄거리 38문서 | 571 |
| 약물·질환·증상 중심 의료 | 1,105 | 4,510 | PMC 논문 70편의 초록·본문 | 12,814 |
| 과제용 의약품 | 270 | 459 | 식약처 e약은요 제품 문서 14개 | 43 |

- **영화:** 출연·감독·제작·각본·리뷰·팔로우 관계와 원본 속성을 모두 사용합니다. 영화별 문서는 영어 위키백과에서 수집한 **도입부 + 전체 줄거리(Plot)**를 생략 없이 합친 본문입니다. 제목·출처·위키백과 문서 버전은 함께 보존합니다.
- **의료:** 수업용 Hetionet CSV에서 치료(`TREATS`) 755개, 완화(`PALLIATES`) 390개, 질환의 증상(`PRESENTS`) 3,357개를 선택했습니다. 검증된 논문 추출 5노드·8관계를 더했습니다. `PALLIATES_CS`의 `_CS`는 Compound→Symptom 구분이며 `PALLIATES`는 Compound→Disease 관계입니다.
- **의료 출처:** `curated`는 Hetionet 기록, `reported`는 논문 보고입니다. 모든 관계가 검색 대상 논문 70편에서 추출된 것은 아닙니다. 연구 보고를 승인이나 효과 입증으로 바꾸지 않습니다.
- **과제:** 제품 문서에서 추출한 효능·이상반응·주의 대상·상호작용·성분·제조사 관계입니다. 추출되지 않은 내용과 효능의 조건은 원문에서 확인합니다.

위 표는 개체와 도메인 관계 수입니다. 문서·청크도 Neo4j에 함께 저장합니다.

영화: `Chunk -[:FROM_DOCUMENT]-> Document -[:ABOUT_MOVIE]-> Movie`

의료·의약품: `Entity -[:FROM_CHUNK]-> Chunk -[:FROM_DOCUMENT]-> Document`

영화의 `ABOUT_MOVIE`는 문서의 주제 연결입니다. 영화·인물에 `FROM_CHUNK`를 만들거나, 이름 언급으로 사람과 청크를 연결하지 않습니다. 의료·의약품의 `FROM_CHUNK`는 검증된 관계 인용 범위와 겹치는 청크를 연결합니다. 일부 인용만 포함한 청크는 그 청크만으로 관계 전체를 설명할 수 없습니다.

적재 시 도메인 개체에 원래 레이블과 함께 `RAGEntity`를 추가합니다. 예를 들어 `:Movie:RAGEntity`, `:Person:RAGEntity`, `:Compound:RAGEntity`로 저장됩니다. 교안에서 공통 `standard_id` 고유 제약과 ID 조회를 위해 추가한 레이블이며, 원본 데이터셋의 레이블은 아닙니다. `Document`·`Chunk`·`RAGImport`에는 붙이지 않습니다.

`Document.id`는 문서 ID, `Chunk.id`는 `문서ID:chunk:번호:원문해시`, 개체는 기존 `standard_id`입니다.

| 자료 | 문서·청크 포함 노드 | 출처 연결 포함 관계 |
|---|---:|---:|
| 영화 | 780 | 862 |
| 의료 | 13,989 | 17,333 |
| 의약품 | 327 | 1,046 |

위 합계는 해당 자료만 세며, 적재 완료 표시 노드는 제외합니다.

그래프 데이터셋은 `movies_complete`, `paper_focus`, `drugs`로 구분합니다. 기존에 적재한 다른 데이터는 검색에 섞이지 않습니다. 영화 관계 기록의 `source_doc_id`는 `movies_sample:`으로 시작하며 위키백과 원문 문서 ID와 구분합니다. 영화 서술문과 논문 출처는 각 문서의 `url`, 제작 근거는 `data/sources.json`과 `data/drugs_sources.json`에 있습니다.

## 실행 준비

1. 노트북, `graph_data.py`, `data` 폴더 전체를 함께 받습니다. `data/embeddings`의 배포 `.npz` 파일도 필요합니다.
2. 저장소 최상위에서 `uv sync`로 만든 `.venv`를 커널로 선택합니다. 패키지 버전은 저장소 최상위 `pyproject.toml`에 있습니다.
3. 이 폴더의 `.env.example`을 `.env`로 복사해 `OPENAI_API_KEY`, `NEO4J_URI`, `NEO4J_USER`, `NEO4J_PASSWORD`를 채웁니다. 상위 폴더의 `.env`도 읽습니다.
4. 위에서부터 실행합니다. Neo4j 2026.01 이상을 사용하며, 연결 후 호스트·포트를 확인합니다.

영화·의료·의약품의 `data/*_schema.json`에는 앞 단원과 같은 `node_types`, `relationship_types`, `patterns`가 있습니다. 노드·관계의 정의와 속성, 관계 시그니처를 읽어 Text2Cypher에 주입합니다. 스키마를 DB에서 조회하지 않습니다.

`material_dir`, `read_json`, `save_json`, `run_cypher`는 지난 단원과 같은 방식입니다. `load_graph`는 `data/*_extraction_packet.json`과 의료 관계 CSV를 읽습니다. 패킷의 `builder_runs`에 문서·청크·개체 연결이 이미 저장되어 있습니다. 그래프 적재·배포 벡터 검사·결과 출력과 그림은 `graph_data.py`가 지원합니다. `graph_data.py`에는 클래스가 없습니다. `QueryGraph`와 GraphStore 규약은 교안 02의 참고 표에서 설명하며, 현재 실행 구조에는 필요하지 않습니다. 도구도 셀에 직접 정의해 `create_agent`에 연결합니다.

그래프 적재는 같은 ID를 재사용합니다. 앞 단원의 Movies 이름 유일성 제약(`movie_title`, `person_name`)이 있으면 조회용 ID 제약으로 전환하며 기존 노드·관계는 보존합니다.

`neo4j-graphrag==1.18.0`의 `VectorRetriever`를 사용합니다.

## 문서를 다시 임베딩하지 않습니다

**학생은 저장된 문서 벡터를 적재하고, 검색 질문만 OpenAI로 임베딩합니다.** 모델은 `text-embedding-3-large`, 768차원입니다.

- 강사가 미리 나눈 청크(500자·겹침 목표 100자)를 패킷에서 읽습니다. 학생은 다시 나누지 않습니다.
- 도메인별 적재 셀에서 `store_graph`, `store_sources`를 바로 호출합니다. 개체·문서·청크·출처 연결과 `Chunk.embedding`을 Neo4j에 함께 저장합니다. `VectorRetriever`가 자료별 벡터 인덱스를 검색합니다.
- 원문·청크 ID·모델·차원을 확인한 뒤 저장된 벡터를 직접 넣습니다.
- 새 PC에서도 배포 파일로 Neo4j에 적재합니다. 기존 청크와 같은 벡터는 재사용합니다.
- 파일이 없거나 버전이 다르면 중단합니다. 자동으로 문서 임베딩을 요청하지 않습니다.

의료 그래프를 줄인 뒤에도 논문 원문과 계산된 벡터는 재사용했습니다. Text2Cypher와 에이전트는 `gpt-5.6-luna`를 사용하며 LLM 호출은 별도로 발생합니다.

## 결과 확인

| 확인할 것 | 읽을 값 |
|---|---|
| 실제 선택한 도구 | `tool_calls` |
| 생성 쿼리와 관계 근거 | `cypher`, `rows`, `claim_id` |
| 검색 원문과 출처 | `chunks`, `chunk_id`, `source_doc_id` |
| 최종 답변과 인용 | `answer` 문자열, `evidence_ids` 목록 |

최종 `evidence_ids`가 실제 검색 결과에 있는지 확인하고, `answer`의 내용은 원문·관계 근거와 직접 대조합니다. 과제의 검색 평가는 관계 ID 또는 문서 ID를 정답 기준과 비교하며 중복 ID는 한 번 셉니다.

빈 조회 결과와 실행 오류는 구분합니다. 답할 근거가 없으면 `answer`에 확인할 수 없다고 쓰고 `evidence_ids`는 빈 목록으로 반환합니다. `EXPLAIN`의 조회 검사와 `READ_ACCESS`는 DB 권한 통제를 대신하지 않습니다.

과제의 작은 검사 예제는 `data/assignment_checks.json`에 있습니다. 검사 셀은 학생 함수의 결과와 실제 검색 결과를 확인합니다.

LV1은 교안 01처럼 관계 조회·벡터 검색 에이전트를 따로 만들고 질문을 하나씩 실행합니다. 실제 도구 호출·답변·인용을 확인하며, LLM과 질문 임베딩 호출 횟수는 재검색에 따라 달라집니다. LV2는 같은 도구들을 한 에이전트에 연결해 선택·답변·평가를 통합합니다.

## 추가 자료

### DB에서 이름 후보 확인하기

`select_names`는 `@tool`로 정의한 DB 조회 도구입니다. 이름·별칭 목록을 Neo4j의 `name`·`aliases`와 대조해 `standard_id`, 등록 이름, 타입을 정렬한 뒤 최대 20개 반환합니다. 파일의 노드 목록은 순회하지 않습니다.

교안 01·02 모두 `create_agent`가 필요할 때 `select_names`를 호출해 이름을 확인하고 Cypher를 작성합니다. 교안 01·LV1은 관계·원문 검색 에이전트를 각각 실행하고, 교안 02·LV2는 두 검색 도구를 한 에이전트에 연결합니다. 관계 조회는 `search_graph(cypher)`가 실행하며, 학생은 생성 쿼리·근거·답변을 확인합니다. `ProviderStrategy(GroundedAnswer, strict=True)`로 답변 형식을 지정합니다. 도구의 `invoke` 결과는 리스트·딕셔너리로 바로 확인합니다. 원문 검색은 `search_documents`로 상위 3개 청크를 읽고 질문에 맞는 근거를 고릅니다. 이름 후보는 관계 근거로 인용하지 않습니다.

교안 01은 `show_citations`로 답변·인용 원문·출처를 함께 읽어 의미를 확인합니다. 본문과 핵심 코드 모두 `paper_answers.json`에 같은 `graph`, `text` 필드로 답변을 저장합니다.
