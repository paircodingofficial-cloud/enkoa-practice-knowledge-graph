# 기존 그래프에 새 관계만 추가하기

**기존 결과를 DB에 준비 -> 새 관계만 추출 -> 검사와 ID 연결 -> 추가 적재 -> 재실행과 되돌리기** 순서입니다.
초기 준비를 마친 뒤에는 기존 관계를 다시 추출하거나 교체하지 않습니다.

| 자료 | 하는 일 | 다음 단계의 입력 |
|---|---|---|
| [교안 01](교안_01_기존_그래프_준비와_새_관계_추출.ipynb) | 기존 그래프 준비, 새 관계 전용 스키마, 추가 추출과 스키마, 근거 검사 | 영화와 의료의 새 관계 파일 |
| [교안 02](교안_02_표준_ID_연결과_새_관계_증분_적재.ipynb) | ID 연결, 문서와 청크 재사용, 새 관계 적재, 계층 조회와 되돌리기 | 기존 관계를 유지한 그래프 |
| [과제 LV1](과제_LV1_새_관계만_추출하기.ipynb) | 기존 pandas 사용 중단 관계 준비, 대체 API만 추출 | assignment_extraction_packet.json |
| [과제 LV2](과제_LV2_기존_그래프에_추가하기.ipynb) | 대체 API 연결과 추가, 재실행과 기존 관계 보존 확인 | 자가채점 결과 |

정답과 해설은 수업이 끝난 뒤 강사가 공유합니다. 교안 마지막 **핵심 코드 이어서 보기**는 학생용에도 완성 코드가 있으며, 의료 데이터로 본문과 같은 과정을 실행합니다.

## 실행 환경과 순서

- 저장소 최상위에서 `uv sync`로 만든 `.venv`를 커널로 선택합니다. 패키지 버전은 저장소 최상위 `pyproject.toml`에 있습니다.
- 현재 작업 폴더에서 상위로 찾아 가장 가까운 `.env`를 읽습니다.
- 필요한 키는 `OPENAI_API_KEY`, `NEO4J_URI`, `NEO4J_USER`, `NEO4J_PASSWORD`입니다.
- Neo4j 5.26 이상의 실습용 DB를 사용합니다. 이 폴더의 `.env.example`을 `.env`로 복사해 접속 정보를 채웁니다.
- 추출 모델은 `gpt-5.6-luna`, 청크 임베딩은 `text-embedding-3-large`, 768차원입니다.
- 청크 크기 500자, 겹침 100자를 사용합니다.

1. 교안 01에서 해당 실습의 그래프를 삭제하고, 저장본의 노드와 기존 관계를 차례로 적재합니다. 이어 영화와 의료의 새 관계 파일을 만듭니다.
2. 교안 02는 기존 DB와 그 파일을 읽습니다. 표준 ID 조회는 이 교안에서 시작합니다. LLM 호출 없이 ID를 연결하고, 문서와 청크를 고정 키로 저장한 뒤 새 관계와 출처 연결을 추가합니다.
3. 과제도 LV1에서 기존 상태와 새 관계 파일을 준비한 뒤 LV2로 이어갑니다.
4. 교안을 처음부터 다시 시작할 때는 교안 01의 초기화 셀부터 실행합니다. 추가 적재만 반복할 때는 교안 02의 되돌리기까지 실행한 뒤 시작합니다.

독립 핵심 코드도 교안 01 -> 교안 02 순서입니다. 교안 01 핵심 코드는 의료 그래프를 초기화한 뒤 기존 관계를 적재합니다.

## 데이터와 확인할 결과

| 사용처 | 이미 DB에 준비할 관계 | 이번에 추출할 관계 | 원문 기준 추가 수 |
|---|---|---|---:|
| 일반 실습: 영화 서술문 | 출연 ACTED_IN 8건 | Movie -> HAS_GENRE -> Genre | 1 |
| 함께 따라하기: 의료 논문 | 치료 TREATS 3건, Hetionet PALLIATES 1건 | Compound -> PALLIATES_CS -> Symptom | 6 |
| 과제: pandas 릴리스 노트 | 사용 중단 DEPRECATES 6건 | ApiElement -> REPLACED_BY -> ApiElement | 3 |

- **영화:** The Matrix의 출연 5건과 The Devil's Advocate의 출연 3건을 유지합니다. 장르가 있는 후자의 소개에서 HAS_GENRE만 추출합니다.
- **의료:** 기존 치료 문서는 유지하고 PMC13461326에서 두 약물의 직접 사용 대상인 증상 세 개를 추출합니다. 별도로 서술한 부수적 이점은 제외합니다.
- **pandas:** 2.1.0 발췌에는 대체 API가 있고, 선정한 2.2.0 발췌에는 대체 API가 없습니다. 2.1.0에서 REPLACED_BY만 추출합니다.

모델 응답은 달라질 수 있으므로 실제 관계와 근거를 원문으로 확인합니다. 정상적인 기준 실행의 관계 수는 다음과 같습니다.

| 단계 | 영화 | 의료 | pandas |
|---|---:|---:|---:|
| 기존 관계 | 8 | 4 | 6 |
| 추가 적재 후 | 9 | 10 | 9 |
| 같은 입력 재실행 후 | 9 | 10 | 9 |
| 이번 추가를 되돌린 후 | 8 | 4 | 6 |

기존 의료 원본 `paper_batch.json`은 수정하지 않았습니다. `paper_existing_graph.json`은 검토 완료본입니다. 원문과 달랐던 Tapinarof 인용은 교정했고, 근거 없는 gabapentin의 breast cancer 치료 행은 제외했습니다. Hetionet의 완화 1건은 원자료에 문장 인용이 없어 빈 근거를 유지합니다. 변경 이유는 파일의 `review_notes`에 있습니다.

영화와 의료 출처는 `data/sources.json`, pandas 출처는 `data/assignment_sources.json`에 있습니다. pandas의 기존 관계와 골드는 원문을 읽고 작성한 목록입니다.

## 추출과 적재를 나누는 이유

- **추출 스키마:** 이번에 뽑을 새 관계만 지정합니다. DB 전체에는 이전 관계와 새 관계가 함께 있습니다.
- **MemoryWriter:** 새 그래프를 실행 결과로 받아 원문을 검사하고 기존 ID를 연결할 시간을 확보합니다. 중복 제거 기능 자체는 아닙니다.
- **결과 파일:** 새 추출 전체인 `rows`, 검사 통과 `validated`, 기각 `rejected`, 원문과 설정, `builder_runs`를 보존합니다. 빌더의 전체 그래프에는 청크, 벡터와 출처 연결도 있습니다.
- **교안 02 추가 적재:** 개체와 추출 관계뿐 아니라 문서, 청크와 저장된 임베딩도 적재합니다. 문서는 `doc_id`, 청크는 문서 ID, 청크 순번과 청크 원문으로 만든 `chunk_id`를 사용합니다. 벡터 인덱스는 추가하지 않습니다.
- **출처 재사용:** 빌더의 `FROM_CHUNK`를 표준 개체 ID와 고정 청크 ID로 옮기고, `FROM_DOCUMENT`로 문서에 연결합니다. 같은 입력을 다시 저장해도 노드와 연결 ID가 유지됩니다.
- **변경 범위:** 문서와 청크 저장 확장은 교안 02에 적용했습니다. 과제 파일은 기존 흐름을 유지합니다.

빌더는 별도 출력 클래스 없이 기본 그래프 응답 형식을 사용합니다. `GraphPruning`은 새 추출 결과를 스키마에 맞게 정리합니다. 기존 DB 관계를 지우는 필터가 아닙니다.

## ID, 계층과 재실행

교안 01은 새 추출 전체의 스키마와 근거를 각각 검사하고 두 준수율을 계산합니다. 두 지표의 분모는 같은 새 추출 전체 행 수입니다. 교안 02에서 `validated`의 이름을 ID에 연결해 `ready`와 `pending`으로 나누며, 앞 교안의 `rejected`는 유지합니다. 스키마 검사, 근거 검사와 ID 조회는 함수로 감싸지 않은 코드 셀로 실행합니다.

- 같은 개체는 기존 `standard_id`를 재사용합니다. 새 개체는 원문 검토 후 등록합니다.
- `claim_id`는 출처 문서, 주어 ID, 관계, 목적어 ID로 만듭니다. 같은 문서의 같은 관계는 재사용하고 다른 문서의 근거는 별도로 남깁니다.
- `ON CREATE SET`은 새로 만든 관계에만 근거와 `batch_id`를 기록합니다. 기존 인용을 덮어쓰지 않습니다.
- `BROADER`는 검토해 정한 계층입니다. 개체를 합치지 않고 상위 개념으로 조회하도록 연결합니다. 의료 계층 질의는 기존 TREATS 관계를 조회합니다.
- `ProcessingState`는 문서의 최근 적재 버전과 검사 건수입니다. 결과가 0건인 실행도 기록합니다.
- 되돌리기는 이번 `batch_id`가 처음 만든 관계만 제거합니다. 기존 관계, 문서와 청크를 포함한 모든 노드, 출처 연결, 계층과 결과 파일은 유지합니다.
- 이 자료는 추가 중심입니다. 원문 수정이나 삭제에 따른 기존 관계 교체는 별도 정책으로 설계합니다.
